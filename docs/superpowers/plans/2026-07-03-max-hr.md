# Max Heart Rate Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Capture/derive an athlete's max heart rate and surface it in Settings, per-ride stats, and the AI coach's Athlete State context — without touching the app's existing, separate LTHR-based HR zone display.

**Architecture:** A pure resolver (`lib/max-hr.ts`) computes an effective max HR from three sources — manual entry, an age-based (Tanaka) formula, and the highest heart rate ever observed in synced rides — with manual always winning. Two new nullable `user_profile` columns persist the manual override and the running observed maximum. The resolved value is threaded into Settings, per-ride stat displays, and seven AI coaching prompt builders.

**Tech Stack:** Next.js App Router, TypeScript, Supabase, existing `IntervalsClient` sync pipeline.

## Global Constraints

- Max HR is a standalone value — it does not touch, replace, or feed into the existing LTHR-based HR zone bands in `components/SessionHistogram.tsx`.
- Graceful degradation: if no manual value, no date of birth, and no observed ride data exist, max HR is `null` everywhere — no fallback to a hardcoded constant.
- Manual override always wins over both the formula and the observed value, regardless of magnitude.
- No new charting libraries; no changes to `lib/hrv/*` or `lib/recovery-score.ts`.
- Mobile-first: Settings UI follows the existing `inputClass`/`labelClass` patterns on that page (≥44px touch targets).
- Always run `npm run typecheck` before committing.
- **Scope correction found during planning:** the spec listed 9 `lib/claude/*.ts` files for the AI-prompt integration. Two of them — `lib/claude/dossier.ts` and `lib/claude/ftp.ts` — do not have a CTL/ATL/Form/HRV/Resting-HR "Athlete State" line to append next to (confirmed by reading both files in full): `dossier.ts`'s two exported functions take pre-flattened primitives/formatted strings, never a `UserProfile`, and have no wellness-state line at all; `ftp.ts`'s only exported function (`predictFTP`) takes power-curve/CP-model data exclusively, with no HR or profile field anywhere. Neither clearly falls under CLAUDE.md's "any task that proposes load or intensity changes" rule (FTP estimation and long-term dossier synthesis are not load/intensity proposals). **This plan touches 7 files, not 9**: `plan.ts`, `review.ts`, `interview.ts`, `session-chat.ts`, `chat.ts`, `briefing.ts`, `coaching-notes.ts`.

```ts
import { calculateAge } from '@/lib/age'

export interface MaxHrInputs {
  manual: number | null
  dateOfBirth: string | null
  observed: number | null
}

export interface MaxHrResult {
  value: number
  source: 'manual' | 'estimated' | 'observed'
}

export function resolveMaxHr(inputs: MaxHrInputs): MaxHrResult | null {
  const { manual, dateOfBirth, observed } = inputs
  if (manual != null) return { value: manual, source: 'manual' }

  const estimated = dateOfBirth != null
    ? Math.round(208 - 0.7 * calculateAge(dateOfBirth))
    : null

  if (estimated == null && observed == null) return null
  if (estimated == null) return { value: observed as number, source: 'observed' }
  if (observed == null) return { value: estimated, source: 'estimated' }

  return estimated >= observed
    ? { value: estimated, source: 'estimated' }
    : { value: observed, source: 'observed' }
}

export function batchMaxHeartRate(activities: { max_heartrate: number | null }[]): number {
  return activities.reduce((max, a) => Math.max(max, a.max_heartrate ?? 0), 0)
}
```
